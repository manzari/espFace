# Releasing the espFace app

Targets for 1.0: **F-Droid through the personal repo `fdroid.manzari.dev` now**; Google Play and the App Store later (sections marked *deferred*). Nothing in this repo publishes anything; every upload below is a manual step with the owner's keys.

App ids: Android `dev.manzari.espface` (Gradle needs lowercase), iOS `dev.manzari.espFace`. Licence MIT. No Google services, no analytics.

## Version numbers

`pubspec.yaml` carries `version: <name>+<build>`, e.g. `1.0.0+1`. **No released version or versionCode may contain the digit 4.** Skip it in both: `1.3.0 → 1.5.0`, build `3 → 5`, `13 → 15`, `39 → 50`.

Android versionCodes are derived in `android/app/build.gradle.kts`:

| Output | versionCode | 1.0.0+1 |
|---|---|---|
| AAB / universal APK | build × 10 | 10 |
| `armeabi-v7a` APK | build × 10 + 1 | 11 |
| `arm64-v8a` APK | build × 10 + 2 | 12 |
| `x86_64` APK | build × 10 + 3 | 13 |

Because the build number has no 4 and the ABI digit is 0 to 3, no code ever contains a 4. Flutter's own split scheme (`abi × 1000 + build`, x86_64 = 4xxx) is overridden; 32-bit x86 is not built by Flutter any more, so there is no fourth ABI. arm64 > armv7 so 64-bit devices that accept both get the arm64 APK. Next releases: `1.1.0+2` (20..23), `1.2.0+3` (30..33), `1.3.0+5` (50..53), and so on.

Changelogs live in `fastlane/metadata/android/en-US/changelogs/<versionCode>.txt`; F-Droid looks them up per APK, so each release needs four files (build×10 .. build×10+3) with the same text.

## Signing key (owner creates it)

The release key is never generated by tooling in this repo. Create it once, somewhere outside the repo, and back it up together with the passwords (losing it means users must uninstall to update):

```sh
mkdir -p ~/keys && docker run --rm -it -v ~/keys:/k inhumane-flutter:latest \
  keytool -genkeypair -keystore /k/espface-release.jks -storetype PKCS12 \
  -alias espface -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=Manzari, O=manzari.dev"
```

Then either create `android/key.properties` (gitignored, paths relative to `android/` or absolute inside the container):

```properties
storeFile=/keys/espface-release.jks
storePassword=...
keyAlias=espface
keyPassword=...
```

or export `ESPFACE_KEYSTORE`, `ESPFACE_KEYSTORE_PASSWORD`, `ESPFACE_KEY_ALIAS`, `ESPFACE_KEY_PASSWORD` (`scripts/flutter.sh` passes them into the container). The keystore must be visible inside the container: `DOCKER_EXTRA="-v $HOME/keys:/keys:ro"`. Without a key the release build still runs but prints `WARNING: no release key ... UNSIGNED` and produces unsigned APKs (F-Droid's own build server signs those; for the personal repo they are useless).

Certificate fingerprint for `AllowedAPKSigningKeys` (lowercase, no colons):

```sh
docker run --rm -v ~/keys:/k inhumane-flutter:latest keytool -list -v -keystore /k/espface-release.jks -alias espface \
  | awk '/SHA256:/ {gsub(/:/,"",$2); print tolower($2)}'
```

## Build

All in Docker. On hosts where `dl.google.com` is unreachable add the mirror env from README.md ("Restricted networks"); CI-like hosts need nothing extra.

```sh
cd apps/mobile
scripts/flutter.sh analyze && scripts/flutter.sh test
DOCKER_EXTRA="-v $HOME/keys:/keys:ro" scripts/flutter.sh build apk --release --split-per-abi
DOCKER_EXTRA="-v $HOME/keys:/keys:ro" scripts/flutter.sh build appbundle --release      # Play only
```

Outputs: `build/app/outputs/flutter-apk/app-{armeabi-v7a,arm64-v8a,x86_64}-release.apk`, `build/app/outputs/bundle/release/app-release.aab`.

Release build settings (`android/app/build.gradle.kts`): R8 minify + resource shrinking with `proguard-rules.pro` keeping the plugin packages reached over method channels (flutter_blue_plus, flutter_blue_classic, usb_serial + felHR UsbSerial, nsd, camerax, secure storage, file_picker, the app's own channel); `dependenciesInfo { includeInApk = false; includeInBundle = false }` (no encrypted Google dependency blob, which F-Droid rejects); versionName/versionCode only from `pubspec.yaml`.

Check before shipping:

```sh
BT=/opt/android-sdk-linux/build-tools/36.0.0
docker run --rm -v "$PWD/build":/b inhumane-flutter:latest sh -c \
  "for f in /b/app/outputs/flutter-apk/*-release.apk; do $BT/aapt2 dump badging \$f | grep -E '^package|native-code'; $BT/apksigner verify --print-certs \$f | grep SHA-256; done"
grep -E '^com\.google\.(android\.gms|firebase|mlkit|android\.play|android\.datatransport)' build/app/outputs/mapping/release/mapping.txt   # must print nothing
```

1.0.0 results (throwaway key): versionCodes 11/12/13 (AAB 10), sizes armeabi-v7a 21.3 MB, arm64-v8a 23.4 MB, x86_64 25.0 MB, AAB 65.2 MB (incl. debug symbols and R8 map, not shipped to devices); the only `com.google.*` code is Material Components and Guava (both Apache-2.0); no dependency-info block.

### QR scanner without ML Kit

`mobile_scanner` bundles Google ML Kit (`com.google.mlkit:barcode-scanning`, proprietary) on Android, which F-Droid rejects; its only alternative is the Play Services variant, which is worse. The app uses `qr_code_dart_scan` (MIT) instead: a pure-Dart ZXing decoder on top of the official `camera` plugin (CameraX on Android, AVFoundation on iOS, both BSD/Apache). One scanner for every platform, no flavours, no native build step. The manifest strips `RECORD_AUDIO` and the storage permissions that the camerax plugin declares for video capture.

### AntiFeatures: none

- No non-free dependencies (checked above).
- Map widgets load tiles from `tile.openstreetmap.org`: open data and an open service, not NonFreeNet.
- The GitHub release check is off by default, user-triggered and optional; the app works fully without it. If you prefer to be strict, add `NonFreeNet` to the metadata.

## F-Droid (personal repo, now)

Input format of `~/Workspace/DevOps/fdroidrepo` (read its README): APKs go into `apps/`, per-app metadata is `metadata/<appid>.yml` plus localized assets in `metadata/<appid>/en-US/`. `watch.sh` skips an APK whose package has no metadata file and, if `AllowedAPKSigningKeys` is set, one signed by another key.

One-time setup (after creating the key):

```sh
FDROID=~/Workspace/DevOps/fdroidrepo
cd apps/mobile
# 1. paste the fingerprint into fdroid/dev.manzari.espface.yml (AllowedAPKSigningKeys) and commit it
cp fdroid/dev.manzari.espface.yml $FDROID/metadata/
mkdir -p $FDROID/metadata/dev.manzari.espface/en-US
cp -r fastlane/metadata/android/en-US/images $FDROID/metadata/dev.manzari.espface/en-US/
```

Every release:

```sh
FDROID=~/Workspace/DevOps/fdroidrepo
V=1.0.0
cd apps/mobile
mkdir -p $FDROID/metadata/dev.manzari.espface/en-US/changelogs
cp fastlane/metadata/android/en-US/changelogs/*.txt $FDROID/metadata/dev.manzari.espface/en-US/changelogs/
for abi in armeabi-v7a arm64-v8a x86_64; do
  cp build/app/outputs/flutter-apk/app-$abi-release.apk $FDROID/apps/espface-$V-$abi.apk
done
cd $FDROID && ./deploy.sh          # stage, index, sign, upload, print fingerprint
# or: ./deploy.sh build (no upload) to inspect repo/ first; ./watch.sh picks up the drop on its own
```

Screenshots and the feature graphic are optional for the personal repo (copy `phoneScreenshots/` too if wanted). The repo's `config.yml` has `archive_older: 3`; the metadata sets `ArchivePolicy: 9` (3 ABIs × 3 releases).

For official F-Droid later: the same yml becomes the base of a `fdroiddata` merge request with a `Builds:` entry (`subdir: apps/mobile`, `srclibs: flutter@<tag>`, `output: build/app/outputs/flutter-apk/app-$abi-release.apk`); the build is already FOSS-only and reproducible-friendly.

## Store listing assets

`fastlane/metadata/android/en-US/` holds `title.txt`, `short_description.txt` (≤ 80), `full_description.txt`, `changelogs/`, `images/icon.png` (512), `images/featureGraphic.png` (1024×500) and `images/phoneScreenshots/` (1080×1920). F-Droid and Play read the same layout.

- Icons: `assets/icon/*.svg` → `scripts/icons.sh` (Alpine + rsvg in Docker, then `flutter_launcher_icons`) writes the Android legacy + adaptive + monochrome icons, the iOS set, the store icon and the feature graphic.
- Screenshots: `test/screenshots_test.dart` runs the real app against a scripted device (the fake device's demo UI) and writes PNGs when asked:

```sh
scripts/screenshots.sh     # runs the test with ESPFACE_SCREENSHOTS=1, then strips alpha
```

## Google Play (deferred)

Needs the owner's Play developer account. First upload:

1. Create the app in Play Console: name espFace, default language en-US, app, free.
2. App signing. Play requires Play App Signing for new apps. Two choices:
   - **Recommended: upload your own app signing key** ("Use a different key" → export with Play's PEPK tool from `espface-release.jks`), then generate a separate upload key. Play-installed and F-Droid-installed copies then share one signature, so users can switch sources without reinstalling.
   - Let Google generate the app signing key and use `espface-release.jks` as the upload key. Simpler, but Play and F-Droid builds are then signed differently and cannot update each other.
3. Upload `app-release.aab` (versionCode 10) to an internal testing track first.
4. Store listing: texts and images from `fastlane/metadata/android/en-US/`, category Tools, contact mail@manzari.dev, privacy policy URL above.
5. App content: privacy policy URL, no ads, target audience 18+ (technical tool, not for children), content rating questionnaire (no user-generated content shared, no violence: rated Everyone), news app no, government app no, financial features none, health none.
6. Data safety:
   - Does the app collect or share user data? **No.**
   - Encrypted in transit: not applicable (nothing is collected). Data deletion: not applicable.
   - The OSM tile and GitHub requests are user-initiated fetches of public content that the developer never receives; they are not "collection" in Play's definition.
7. Permission declarations: none of the app's permissions needs a declaration form. Bluetooth scan is `neverForLocation`; `ACCESS_FINE_LOCATION` is limited to `maxSdkVersion=30` (needed for BLE scans on Android ≤ 11, foreground only, no background location). Camera is used only for QR codes.
8. Target API: `targetSdk` follows Flutter's default (36), which meets Play's current requirement.
9. Promote internal → closed testing (new personal accounts need 12 testers for 14 days before production) → production.

## App Store (deferred, needs a Mac)

Prepared without a Mac: bundle id `dev.manzari.espFace`, display name and `CFBundleName` espFace, version from `pubspec.yaml` (`FLUTTER_BUILD_NAME`/`FLUTTER_BUILD_NUMBER`), `ITSAppUsesNonExemptEncryption = false` (HMAC-SHA256 for authentication only, OS TLS), usage strings (local network, Bonjour `_espface._tcp`, camera, Bluetooth), `Runner/PrivacyInfo.xcprivacy` (no tracking, no collected data; required-reason APIs: UserDefaults `CA92.1` via shared_preferences, file timestamps `3B52.1` for the user-picked OTA file), app icon set without alpha. Plugins ship their own privacy manifests.

Not verified here (no Xcode): that the project builds, that the privacy manifest is picked up, CocoaPods/SwiftPM resolution of the camera plugin, BLE and Bonjour behaviour on a real iPhone.

Checklist on the Mac:

1. Install Xcode (current), Flutter 3.44.0, CocoaPods. `cd apps/mobile && flutter pub get && cd ios && pod install` (if the project uses CocoaPods).
2. Apple Developer account: create the App ID `dev.manzari.espFace` (no extra capabilities), and the app record in App Store Connect (name espFace, SKU espface, primary language English, bundle id above).
3. Open `ios/Runner.xcworkspace`, Runner target → Signing & Capabilities: select the team, automatic signing. Check Info.plist and that `PrivacyInfo.xcprivacy` is in Copy Bundle Resources.
4. Smoke test on a device: WiFi device via mDNS, BLE device, QR scan, PIN pairing, OTA push.
5. `flutter build ipa --release` then upload `build/ios/ipa/*.ipa` with Transporter (or Xcode Organizer → Distribute App → App Store Connect).
6. Xcode Organizer → Generate Privacy Report; App Store Connect → App Privacy: "Data Not Collected".
7. Listing: name espFace, subtitle "ESP32 control panel, no cloud", description from `full_description.txt` (drop the Android-only USB/Bluetooth Classic parts: iOS supports WiFi and BLE only), keywords `esp32,iot,ble,arduino,dashboard,maker`, category Utilities (secondary Developer Tools), support URL https://git.hauptstadt.monster/manzari/espFace/issues, privacy URL above, screenshots 6.9" (1320×2868) and 6.5" taken on the Mac simulator.
8. Export compliance is answered by `ITSAppUsesNonExemptEncryption`. Review notes: explain that the app needs an espFace device; offer the fake device (`tools/fake-device`, docs "Fake device") or a demo video.
9. TestFlight first, then submit for review.

## Decisions for the owner

- Create the release key, keep it and its passwords backed up, fill `AllowedAPKSigningKeys`.
- Play: own app signing key (shared signature with F-Droid) vs Google-generated.
- AntiFeatures: none (default) or `NonFreeNet` for the optional GitHub check.
- When the repo goes public: confirm the SourceCode/IssueTracker URLs in `fdroid/dev.manzari.espface.yml`.
